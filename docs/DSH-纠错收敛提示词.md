## 一、背景（给人看）

现在这个 App 的 AI 纠错有个反效果：它**不敢改，只敢标**。

一节课下来，报告里躺着几十条「待确认」，每条都要点开、看候选、选一个、确认。用户点三条就烦了，剩下的一概略过——那这次纠错等于没做，还倒赔了十几分钟。

根子不在模型笨，在三个地方叠在一起：

1. **提示词没有预算**：规则 B 说「拿不准就标待确认」，模型就每处都标，几十条不算多；
2. **程序没有收口**：`_mergePending` 只按「完全相同片段」合并，同义不同写的、长片段的、带标点的各占一条；
3. **术语表太泛**：一节课的术语表动辄三四十条，模型拿它去套全文，套不上的全变成「疑似」。

目标不是「让模型少干活」，而是**让它把有限的人工注意力花在最值钱的几条上**。

一句话方案：**给标注设预算，程序排序截断，术语表减肥，界面批量处理。**

### 目标（可验收）

1. 一节 40 分钟中文课的待确认项 **≤5 条**（英语课同样规则）；
2. 其中至少 3 条是**真误听**（人工回听判定），不是「原文本来就对」的误报；
3. 用户处理完这 5 条 **≤3 次点击**（批量按钮算一次）；
4. 被压掉的低置信项**不能凭空消失**：报告里要有「另有 N 处低置信，未列出」的计数，可展开看；
5. 中文课现有提示词与报告格式不破坏（有快照测试）。

### 硬约束

1. **不许编造**。宁可保留原文，也不许为了「少一条待确认」把错误直接改掉。A 档仍然是唯一允许直接改的档位。
2. **不许静默丢错误**。压掉的是「条目数」，不是「信息」：必须留下 `suppressed` 计数与原因。
3. **可撤销**。批量替换后仍要能撤销（现有 `_undoTranscript` 机制不能绕开）。
4. **位置必须重算**。批量处理多条时，`PendingFixer` 的「替换后重新定位」逻辑要复用，不能就地拼字符串。
5. 英语课走同一套预算，但英语的 B 档本来就少（只许拼写/专名/同音），不要为英语单独发明规则。

### 方案（四层，按顺序做）

#### 第一层：给模型一个「待确认预算」

在两份系统提示词（中文 `_systemPrompt` 与英语 `_englishSystemPrompt`，以及 `CorrectionAgent` 的系统提示词）里，把 B 档从「拿不准就标」改成「按预算标」：

```
## 待确认预算（硬性）
- 全文最多输出 5 条 pending。超过 5 条的，只保留最值得人回听的 5 条，其余不要输出。
- 排序依据（从高到低）：
  1. 命中了术语表中「高优先级」术语的疑似误听；
  2. 同一处疑似在文中反复出现（count ≥ 2）；
  3. 候选唯一、且与原文只差一个音/一个字母；
  4. 其他。
- 以下情况一律不标：
  · 片段长度 < 2 个字符、纯标点、纯数字；
  · 原文本身通顺且不是术语（改不改都不影响笔记正确性）；
  · 你已经能高置信修正的（放 A 档直接改，不要既改又标）。
- 标了就必须给 candidates（1–2 个），不要给空候选。
- 末尾如被预算截断，输出一个字段 `suppressedCount` 表示没列出的条数。
```

程序侧解析 `suppressedCount`，没有就按 0 处理，老输出兼容。

#### 第二层：程序侧统一收口（新文件 `lib/services/pending_budget.dart`）

不要在每个调用点各写一遍截断，抽一个纯函数：

```dart
class PendingBudget {
  static PendingTrimResult trim(
    List<PendingItem> items, {
    int max = 5,
    Set<String> highPriorityTerms = const {},
  });
}

class PendingTrimResult {
  final List<PendingItem> kept;      // 已排序、已截断
  final int suppressed;              // 被压掉的条数
  final List<PendingItem> all;       // 原样保留，供「展开查看」
}
```

处理顺序：

1. **过滤**：`snippet.trim().length < 2`、纯标点数字、`candidates` 为空且 `count == 1` → 丢弃并计数；
2. **归一化去重**：`snippet` 去空白与标点、统一全半角后比较；再对「包含关系」合并（A 是 B 的子串且长度差 ≤2，保留更长的那条，count 相加）；
3. **排序**：命中高优先术语 > `count` 高 > 候选唯一 > 其他；同分按出现位置先后；
4. **截断**：`take(max)`，其余计入 `suppressed`（加上模型给的 `suppressedCount`）；
5. **位置**：保留的项继续用现有 `withLocations` 逻辑重算 positions。

接入点：`TranscriptCorrector.calibrate` 返回前、`CorrectionAgent.run` 返回前。两处都调同一个函数，避免规则漂移。

#### 第三层：术语表减肥

待确认多，一半是术语表喂太宽。改三件事：

1. 生成时限制规模：**高优先级 ≤15 条、中优先级 ≤15 条、低优先级 ≤10 条**；超出的由模型按「本节课最可能被听错」排序后截断；
2. 只收**本节课真的会出现的术语**（按章节主题），不要收整本书的目录词；
3. 生成结果里带 `definition` 的（英语课）不影响预算；中文课不需要新增字段。

术语表变小后，模型「套不上就标」的压力自然下降。这一层要和第二层一起验收，否则分不清收益来自哪。

#### 第四层：界面批量处理

报告区与「已保存的待确认」面板都加三个动作：

| 动作 | 行为 |
|---|---|
| 全部按首选处理 | 对每条 `candidates.first` 调 `PendingFixer.apply`，逐条替换并重算位置；替换前弹一次确认（显示会改 N 处） |
| 全部忽略 | 清空 pending（只清列表，不改正文），记一条 undo 快照 |
| 只看术语类 | 过滤掉非术语命中项（用 `hits` 或 `highPriorityTerms` 判定） |

细节：

- 报告区默认只展示 **前 3 条**，其余折叠成「展开其余 N 条」；
- 每条待确认给一个「忽略」单按钮，不用点进弹窗才能跳过；
- 处理完显示「已处理 N 处，正文已更新」，并保留撤销入口。

### 技术判断与风险

1. **为什么不直接把 B 档删掉**：删了会变成「模型只改它敢改的，其余静默保留」，用户根本不知道哪里可能错。预算 + 计数是「少打扰但不隐瞒」的唯一折中。
2. **为什么不许一键全改后不看**：批量按钮必须带确认弹窗并显示条数；改错一条的成本高于多点一次。批量后仍可撤销。
3. **排序权重是怎么定的**：术语命中 > 重复出现 > 候选唯一 > 其他。理由是前两类「改对了收益最大」，后两类「人一眼能判断」。
4. **`_mergePending` 要不要保留**：保留（跨块合并仍需要），但归一化去重放到 `PendingBudget` 里做，不要两处各写一套。
5. **英语课**：预算同样 5 条；英语的 B 档规则本来就窄，预期 pending 更少，不需要单独调参。
6. **性能**：去重是 O(n²) 的包含判断，n 是 pending 条数（几十），可忽略；不要为此引入索引结构。

## 三、一句话

纠错的价值不在「标出多少处」，在「用户真的处理了几处」。把标注当预算花，比让它无限膨胀更接近可用。
